## 版本 A：三条（推荐，标准简历用）

**AST 驱动的本地 LLM 代码智能引擎**（个人项目 · Python / Tree-sitter / SQLite / Ollama）

- 从零实现 Tree-sitter AST 解析层，支持 Python/Rust/TypeScript/JavaScript 四种语言，
  在 ripgrep（110 文件）、requests（37 文件）、execa（639 文件）三个真实仓库上
  累计索引 **786 文件 / 6,411 符号 / 46,203 条图边，零解析错误**；设计 6 级调用边
  解析策略（作用域 → 接收者推断 → 文件唯一 → 导入映射 → 全局唯一 → 目录唯一），
  并将解析证据写入 `edges.via` 字段，使静态解析率（35.7%–45.6%）可按策略拆解归因。

- 构建嵌入式 SQLite 知识图（FTS5 全文索引 + 级联删除 + 外键约束），实现
  callers/callees/多跳调用链/依赖闭包查询；在 8GB 显存的 RTX 4060 上通过
  Ollama 驱动 qwen2.5-coder:7b（Q4_K_M，占 5.1GB VRAM）完成逐文件摘要、跨文件
  架构分析与开发者指南生成，全量分析累计消耗 **360,370 tokens**（115 次调用，
  平均 3,134/文件，P95 5,812），**156 次调用全部由服务端返回真实 token 计数，
  零字符估算**。

- 设计内容哈希 + prompt 模板版本的二级摘要缓存与依赖闭包增量分析：改 3 个文件时
  只重算其依赖闭包，**5 轮增量平均消耗 9,225 tokens，相比 360,370 的全量基线
  节省 97.4%**；缓存累计命中 98 次、避免 312,342 tokens（**节省 46.4%**）。
  配套 45 个测试（含增量边保留、FTS5 特殊字符、JSON 截断修复、16k 上下文上限），
  修复 11 个实质 bug（含调用作用域取最大跨度、增量索引丢失入边、架构 prompt
  未 clamp 导致 OOM）。

## 面试可能被追问的点（提前准备）

1. **"解析率才 45%，是不是说明方法不行？"**
   未解析的 54% 里绝大多数是 `assert_eq!`、`Ok`、`Some`、`Vec::push` 这类
   **仓库内没有定义**的标准库/宏符号。真正无法提取目标文本的动态调用点只有
   0.17%（29/17,088）。这说明静态分析的上限是"仓库边界"，不是解析器缺陷。

2. **"为什么不用现成的代码分析工具？"**
   项目定位是"从零实现"以验证工程能力。且现成工具（如 tree-sitter-graph）
   通常只做查询，不做 token 记账、缓存分层、增量闭包这套工程闭环。

3. **"7B 模型能做出有价值的分析吗？"**
   架构分析里 8 个符号引用**逐一核实全部真实、行号全部准确**——这是 AST
   grounding 的直接效果（prompt 里给的是 `qualname (path:line)` 而非源码片段）。
   但开发者指南里的**代码示例不可编译**，这是模型能力的真实边界，已如实记录。

4. **"增量节省 97.4% 是怎么算的？"**
   全量基线 360,370 是同一仓库同一模型的真实全量消耗；增量 5 轮各改 3 个文件，
   每轮只对依赖闭包（2–3 文件）调用 LLM，平均 9,225。`1 - 9225/360370 = 97.4%`。
   注意这是"改动极少文件"的场景，改动多时节省比例会下降。
